# Native backup and recovery

Full backups are portable directories under the selected native profile root's `full-backups/`. Copy the complete directory, including `manifest.json`, when moving it elsewhere. The application does not upload these files. No new archive dependency is required and no archive extraction paths are accepted.

Each completed directory contains a SQLite Backup API snapshot (`user.sqlite`), saved desktop settings, renderer state (application localStorage and learned scanner references), and original content-addressed screenshot evidence. Catalog/query caches and live WebView files are excluded. The native database snapshot is transactional; renderer state is a separate snapshot captured at the start of the operation. Unsaved scan-form edits must be saved before backup. This is not a cross-store transaction or a cloud backup.

Files stream through a bounded hashing/copy buffer. Each manifest entry has an exact length and SHA-256. Only named database/JSON files and lowercase SHA-256 screenshot names are allowed. Per-file, screenshot, JSON, file-count and total bundle limits are checked. SQLite quick integrity/foreign-key checks and screenshot references from retained stacks/drafts must pass. A failed operation leaves its `.incomplete-*` directory, does not advertise it as a completed backup and never removes source data. Full backups currently have manual retention; daily progress JSON files remain a distinct, narrower existing feature.

Import verifies the source without migrating it, then creates a new staged profile under `recovered-profiles/`. The source backup and current profile are retained. Database migrations run only on the restored copy. After validation the directory is finalized and the UI offers explicit activation/restart. A small atomic `active-profile.json` pointer selects the recovered profile on startup. No live SQLite/WebView database is overwritten. The UI can return to the original profile; pointer history is retained instead of deleted. An incomplete restored profile cannot be activated.

Recovered renderer state is validated and installed before persisted stores are imported or appearance preferences are hydrated. The operation is idempotent until acknowledged by a durable marker. Correction fingerprints must match their declared grid dimensions and scanner format. A startup error exposes a return-to-original action. Corrupt settings stay on disk with settings writes disabled; a failed inventory worker leaves the rest of the app and recovery UI available. These are implementation contracts, not a claim that the Windows restore lifecycle has already been exercised.

No tests were created or run, following the user's instruction. Compiler/lint/build checks are recorded in the execution ledger. Manual recovery, interrupted disk writes, low-disk conditions, original-install coexistence and Windows restart behavior remain unverified acceptance gates.
