# Bounded verified updater payload staging

Goal: extend the explicit updater preview with a separate download-and-verify step while installation and normal production updates remain disabled. This does not complete the release/update lifecycle gate.

Discovery saves one native candidate (URL, signature, announced version, monotonic discovery time and opaque ID). A new check invalidates the previous candidate, including on failure. Downloads accept only that ID from the main window, never a caller-provided URL/key/signature, and require a candidate younger than ten minutes. Check/download share one in-flight guard; actual blocking download owns the guard even if its caller disappears. Benchmark/default builds cannot download.

Use HTTPS-only transport with public-domain-form URLs, credential rejection, up to five permitted redirects, 20-second connection timeout and five-minute whole-request timeout. Reject advertised sizes above 512 MiB and enforce the same limit during streaming with one-byte overflow detection before retaining excess data. Empty payloads fail. The bounded payload is retained for signature verification; Vec allocation capacity and total process memory are not guaranteed to equal the byte limit. There is no user-cancellation command in this step.

Verify the Minisign artifact and global/trusted-comment signatures against the compiled fork public key using minisign-verify, consistent with the installed Tauri updater's verification path. Only after successful verification read exactly one signed version field from the trusted comment and require it to match the announced version (optional leading v ignored). Missing/older unversioned signatures are rejected. This requires a signing CLI that includes version metadata; older signatures cannot silently bypass version binding.

Only verified payloads are written through the existing flush-and-rename writer into profile_root/updater-staging/<sha256>.verified-update. No executable extension, installer execution, launch/restart, deletion or automatic cleanup is added. Copies remain manually retained; staged files are excluded from full saved-state backups. Repeated identical payloads use the same checksum path. A future installation command must reverify bytes against signature/version immediately before use; a historical successful download is not proof that a file stayed unchanged on disk.

The opt-in preview UI offers a separate download button, shows the cap/retention and reports verification/hash/path. It continues to return installable=false. It does not promote candidates into the incumbent production updater's ready state. Read-only discovery still uses the upstream plugin's metadata parser; its response-size budget remains a separate open item.

Verification semantics were checked against the installed updater 2.14.1 and minisign-verify source. No tests, fixture signatures, keys, live discovery/download, installation, publication or screenshot workflows were created or run. Public channel/key information and full signed update/recovery acceptance remain open; installer artifacts were not refreshed.
