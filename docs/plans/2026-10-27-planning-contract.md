# Inventory planning contract

The native database owns physical inventory and per-profile planning preferences. Existing React stores remain authoritative for quest completions and built hideout levels during this migration; the application does not introduce another quest tracker. A request contains normalized requirements and catalog/progression revisions, never renderer-supplied physical inventory. The database actor checks the expected planning revision and exact container revision map before reading stock and calculating.

The declared horizon includes unfinished faction quests, selected hideout target levels (all known levels by default, plus dependency closure) and explicitly selected craft/barter batches. Inferred quest completion and aggregate Item Collection counts do not prove a hand-in and are not subtracted. Partial objective hand-ins are not yet represented; full objective amounts are conservatively reserved. Wiki-only quests and unsupported item-state constraints remain explicit coverage gaps.

Consumptive requirements sum. Accepted alternative item IDs remain one demand, rather than reserving each alternative independently. Global integral allocation prevents using one unit for two consumptive requirements. FIR-only requirements compete with unrestricted ones, with unrestricted demand preferring non-FIR stock. Duplicate returned tools in a single recipe sum; tools shared across sequential crafts reserve the largest simultaneous requirement. This is an explicit sequential-crafting assumption, displayed in the UI. It does not assert simultaneous-crafting support or trader availability.

An additional buffer is added to consumptive demand. A minimum-total reserve overlaps already protected stock. Never-sell protects all matching physical copies. Unknown identity, quantity or FIR does not authorize a sale or satisfy a confirmed demand. Missing container coverage, stale inventory/catalog facts, legacy unlocated counts and unsupported requirements prevent surplus advice. Each portion retains its location, snapshot, allocation sources and reason.

The renderer hides calculated advice after input revisions change, inventory events or freshness confirmation is lost. An active complete plan expires at the catalog deadline without an idle polling loop. The result is advice over named revisions, not a sale operation. Native backup, partial/scrolled views, objective hand-ins and price estimates are separate remaining work.

API shape evidence was refreshed on 2026-10-27 from `https://json.tarkov.dev/pve/crafts` and `https://json.tarkov.dev/pve/barters` using read-only requests. Craft `requiredItems[].attributes.tool` and barter `offeredItem` were observed. A barter input quantity of `155.1` was observed; the parser preserves it as an unsupported quantity rather than rounding. These source observations are not a recognition benchmark or a test run.
