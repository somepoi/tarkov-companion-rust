# Explicit staging installer and startup outcome

Goal: connect the verified staging payload to a recoverable Windows installer transition without enabling normal production updates or executing an installer during development.

Keep the original native updater Update object with each discovered candidate. A separate install command accepts only the fresh candidate ID, exact displayed version, checksum, saved-draft assertion and renderer backup. It requires Windows, staged-updates, a compiled TC_STAGED_INSTALL_ENABLED=1, the main window and non-benchmark mode. Runtime environment changes cannot turn this on. Track the public switch through build rerun directives. The default value stays off and normal updateMode/update routes stay disabled.

Acquire the shared updater job and exclusive native IO gate, retaining them inside the actual blocking operation. Reopen only a checksum-named bounded regular staging file inside the staging directory; reject symlinks/outside paths, size/growth overflow and checksum changes. Repeat pinned-key artifact/global signature and signed-version checks on the in-memory bytes. Create a fresh full recovery bundle under the gate, then durably write a pending receipt containing expected version, backup name and digest. Only then call the official updater Update::install(bytes), which also verifies the bytes. On Windows this API launches its installer and exits the process; no custom shell command or caller-supplied executable path is used. A failure leaves the receipt and backup for recovery. Installer launch/execution is not observed by this change.

The explicit preview UI shows the destructive transition only when the native download response reports the compiled switch enabled; its button names backup, app close and the selected version. Disabled builds retain the recovery-copy-only action. Unsaved renderer data remains governed by the explicit save/idle assertion and existing snapshot separation; the native gate is not a cross-window WebView storage transaction. No installer cleanup/downgrade/schema reversal is introduced.

A bounded pending receipt is consumed only by the main window and archived under a new outcome name. Parsing validates semver and the locally constructed backup-name grammar. Report whether the currently running version is at least the requested version; this does not claim installer history or byte identity. Serialize receipt consumption, cache its startup result in process so repeated React mounts receive the same outcome, and guard it as native IO so a banner remount cannot consume a receipt while installation preparation holds the gate. The banner handles native failure with a recovery path instead of offering unsupported Electron installer commands, and surfaces receipt read errors. Existing Electron outcomes retain their behavior.

The plugin's Windows install/verify/exit semantics were inspected in installed tauri-plugin-updater 2.14.1 source. Full signing-channel/installer coexistence/upgrade/recovery validation still requires external release assets and observations. No channel/public key has been inferred or generated, no guest updater permissions were added, and no installer was executed or published.

Verification on 2026-11-01: staged/default strict Clippy, clean frontend lint/TypeScript, Tauri and Electron frontend production builds (including Electron main/preload), final native staged/default builds (22.44s/21.75s), notices (317 crates/195 texts), formatting and whitespace checks exited 0. Source review traced build-switch admission, original Update object ownership, bounded file revalidation, immutable verified bytes, fresh backup/receipt-before-install ordering, main-window receipt serialization/cache and native/Electron banner separation. Repeated-mount receipt consumption was corrected during source review. No tests, receipt fixtures, update/restore simulations, real signatures/downloads, installer runs or screenshot workflows were created or run. Installer packages were not refreshed; release/runtime gates stay open.
